# Reader feedback on the Legislation Trackers: implementation plan (Oct 8 2026)

Six points of reader feedback on the fiscal tracker and the Sep 2026 Substack post, each checked against the live code and data before planning. Record counts below were read directly from `data/fiscal_impacts.json` and `laws.json` on Oct 8 2026 (474 fiscal records; 2,159 enacted laws).

## What the code and data actually show

| Feedback | Finding |
|---|---|
| 1. Lightest pink = no spending on the Substack chart | The chart is the Agency Powers stacked bar (`legislation_implementation_tracker/powers/agency-powers/`, image 3 in the post). The empty bar track is `var(--blue-light)`, which the Powers theme repoints to a pink tint, and the "Everything else" segment is `var(--blue-mid)`, the same family. Same pattern on `agency-workload/`. The reader read the track as a data category. |
| 2. Click through from charts to bills | The bill table already has a `?intro=NNN` deep link (expands the row). Nothing else is wired: no Chart.js `onClick` on any page, no URL params for agency/sponsor/year filters, `MSFilter` has `selected()`/`pass()`/`reset()` but no setter, and agency profiles link fiscal rows to the bare tracker root rather than the bill. |
| 3. Bill status + lapsed / in progress / passed | No status field exists in the fiscal data. 400 of 474 records are enacted laws (in `laws.json`); the other 74 are all 2026-session bills still pending. Zero lapsed bills are in the table today. Legistar's detail page exposes status in `lblStatus2` (checked live: Int 0518-2026 reads "Laid Over in Committee"), one regex away from the `lblFile2` read the fetcher already does. |
| 3.2 Historic lapsed bills | Not covered. The enacted-law seed only walks passed laws, and Legistar's public attachment search only returns 2024+ matter IDs. Lapsed bills from the 2018-2021 and 2022-2025 sessions that carried a fiscal statement need the REST enumeration path (`rest_years`), which is built and proven but API-billed for the extraction step. |
| 4. Actual spend vs estimate | The city budget is accounted by agency and unit of appropriation, never by local law, so there is no general per-bill actual. Not buildable as a tracker feature. |
| 5. Split bill summary from fiscal impact | Every fiscal statement has a "Summary of Legislation:" section before "Effective Date:" (133 of 133 cached statements checked). The pipeline never captured it; the detail panel shows only the title and the two "Impact on" narratives. 738 statements are cached locally as .docx, so a backfill is a regex pass with no model calls. `laws.json` also carries Legistar's own `summary` for enacted bills as a fallback. |
| 6. Red bars on positive values | Confirmed on three pages. `sponsor-fiscal-impact`, `agency-fiscal-impact` and `intro-year-impact` colour negative `rgba(220,38,38)` and positive `rgba(207,75,12)` (tangerine, reads as red beside the red). `cost-revenue-breakdown` uses green for positive. All four hardcode colours, against the brand rule. `assets/chart.css` already defines a diverging pair (`--c-div-neg-*` warm, `--c-div-pos-*` cool blue) that none of them use. |

## Plan

### Phase A: fixes with no API cost (one builder session, then a refuter pass)

1. **Colour of positive bars (item 6).** Replace the hardcoded rgba pairs on the four fiscal chart pages with one shared semantic pair from `chart.css`: cost = `--c-div-neg-2`, revenue gain = `--c-div-pos-2` (hover: the `-3` steps). Add the pair as named tokens (`--c-fiscal-cost`, `--c-fiscal-gain`) in `chart.css` so the stat pills, legend swatches and the overview's cost/revenue rows use the same two colours. Check the metric-button "negative" state and the `.legend-swatch` rules on the cost-revenue page at the same time.
2. **Neutral bar track (item 1).** On `agency-powers/` and `agency-workload/`, set `#chartArea .c-bar-track` to a neutral (`--b-line` at reduced opacity, or the cream `--b-cream-2` if defined) and move "Everything else" to `--b-ink-4`. Then re-screenshot the Agency Powers chart and swap image 3 in the published Substack post through the shareout session (the post is live; the image is the only edit).
3. **Bill status (item 3).** Pipeline: `parse_legistar_page` also reads `lblStatus2`; every record gets `status` (Legistar's string) and `status_group` with three values: `passed` (Enacted), `in_progress` (Committee, Laid Over in Committee, Hearing Held, Reported, Approved by Council, Returned Unsigned, any other open state), `lapsed` (Filed (End of Session), Withdrawn, Vetoed, Disapproved by Mayor, Failed). Enacted records take status from `laws.json` with the law number; the monthly Action re-reads the 74 pending pages so a bill that passes or lapses moves group (token-free, about a minute). Page: a status pill in the row and detail panel, a "Status" `MSFilter` group with the three categories plus the raw Legistar statuses, and the overview's stat pills counting "X passed, Y in progress, Z lapsed". The validator gets a soft check for records with no status. Methodology page defines the three categories and says in plain words that lapsed bills before the 2026 session are not yet in the table (until Phase C runs).
4. **Summary of legislation (item 5).** Pipeline: a code-only extractor (regex between "Summary of Legislation:" and "Effective Date:", run on the docx text before the Claude call) writes `summary_of_legislation` on every record; backfill from the 738 cached statements, re-downloading any missing ones by `attachment_id` (no model calls). Detail panel: "What the bill does" (verbatim summary) above "Fiscal impact" (the two narratives, unchanged), with Legistar's `laws.json` summary as the fallback when the section is absent. Add the summary to the Ask index and the static snapshot builder.
5. **Link agency profiles to bills.** `agencies/index.html` `section3Fiscal` rows link to `../../nyc_council_fiscal_impacts_tracker/?intro=<number>` instead of the tracker root. Same for the fiscal rows on member profiles if they link to the root.

### Phase B: click-through from charts (item 2), after A ships

1. `MSFilter.prototype.set(values)` (select exactly these values, fire onChange) in `assets/multiselect.js`, with a `?v=` bump on every page that loads it.
2. Bill table reads `?agency=`, `?sponsor=`, `?committee=`, `?fy=`, `?status=` (comma-separated), applies them through `set()` on load, and scrolls to the table; `?intro=` keeps its current behaviour. Filter state is also written back to the URL on change so a reader can share a filtered view.
3. Chart.js `onClick` on the agency, sponsor and intro-year bars navigates to the bill table with that filter plus whatever filters the chart page already has selected. Bars get `cursor: pointer` and a one-line hint under the chart ("Click a bar to see its bills"). The cost-revenue page's per-bill bars go to `?intro=`. The overview's ranked rows (agencies, sponsors) become links the same way.
4. Tooltip enrichment (optional, after 3): each bar's tooltip lists its three largest bills by net impact. The agency chart's `data.json` already carries per-agency bill lists; the sponsor and year pages compute from `fiscal_impacts.json` in the page.

### Phase C: historic lapsed bills (item 3.2), needs Tal's approval for API spend

The REST path finds fiscal statements on non-enacted bills that the public search cannot reach. Run it session by session through `refresh_fiscal_data.yml` `rest_years` (2022-2025 first, then 2018-2021): phase 1 enumeration is token-free and reports how many matters carry a statement before any model call, so the approval request can state the exact call count and cost. Expectation from the Sep 3 2026 test on 2014 (0 statements among 1,569 non-enacted intros): statements are written at the committee-vote stage, so lapsed bills with one are the ones that passed committee and died at session end. Each new record arrives with `status` "Filed (End of Session)" from Phase A's scrape, so the three-category filter fills in without further page work.

### Item 4: actual spend, declined with a reason

No per-law actual exists in any city dataset; the methodology page should say so in one sentence under the fiscal tracker's limits. Two partial substitutes, neither a tracker feature: the agency profiles already show each agency's adopted budget and headcount beside its bills, and a hand-curated post could compare estimate to actual for the few laws that created their own budget line (CityFHEPS, Fair Fares, the commercial waste zones). Logged as a post idea, not built.

## Docs and checks that move with the change

`fiscal-impacts-tracker` skill (schema table: `status`, `status_group`, `summary_of_legislation`; colour tokens; URL params), `legislation-trackers` skill (MSFilter `set()`), fiscal methodology page, `build_fiscal_static_snapshots.py`, `build_ask_index.py`, `validate_fiscal_impacts.py`, `tests/test_fiscal_rules.py` (status grouping and summary parsing get unit tests), and a reply to the reader once Phase A is live.
